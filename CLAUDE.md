# CLAUDE.md — DEBiLGI

Читается автоматически при каждом запуске. Подробности архитектуры — в `.codex_work/ARCHITECTURE_MAP.md`:
**прочитай карту первой** и читай код только там, где он нужен для задачи. Не изучай весь репозиторий заново.
Если менял архитектуру — обнови соответствующие места карты в конце этапа.

## Проект
Discord-бот на Python 3.13 + SQLite **без нейросетей в мышлении** (решение владельца 2026-11-20: допускается одна личная маленькая нейросеть-«грамматист» только для поверхностной сборки фраз): символьный разбор, смысл, планирование и генерация
русской речи. Работа идёт этапами; задание этапа — в промпте, итог — в `.codex_work/LAST_MESSAGE*.md`.

## Принципы (нарушать нельзя)
1. Без нейросетей и LLM-генерации в мышлении бота: что сказать, факты, ход, тон, выбор слов решает только DEBiLGI. Исключение (владелец, 2026-11-20): личная маленькая нейросеть-«грамматист» отдельным слоем — получает готовый план (леммы, роли, привязки), выдаёт только порядок, словоформы входных лемм и служебные слова из закрытого класса; своих слов и смыслов не добавляет, ничего не пишет в meaning_claims, при низкой уверенности — fallback на детерминированную сборку; включается флагом.
2. Перестраивать существующие механизмы, а не добавлять слои, сервисы, таблицы знаний.
3. Никаких шаблонов ответа и захардкоженных фраз, включая фразы из живых примеров. Исправление — механизм.
   Поверхность ответа всегда из `MessagePlan` → `ResponseComposer` и наблюдённых частей.
4. Гипотезы не становятся фактами без подтверждения людьми днём (один автор = один голос).
   Сон, повторы бота, корпус и уверенность фактом не делают.
5. Мышление и сон не съедают и не блокируют дневные ответы.
6. Веса двигаются опытом, не руками.
7. Врождённые правила — только пустой плейсхолдер; конкретные правила не писать.
8. Личные факты не переносятся между людьми; ничего не переносится между серверами.

## Окружение и ресурсы (важно)
- Машина: 8 CPU, ~15 ГБ RAM. Один probe-сервер с сидом занимает ~3–6 ГБ.
  **Не больше двух тяжёлых процессов одновременно** (сид, probe-сервер, полный pytest, сценарий «дня»).
  Таймируемые замеры скорости — без любой параллельной нагрузки.
- **Всегда `PYTHONPATH=/workspace/DEBiLGI-codex/src`**: `.venv` содержит editable-установку чужого дерева
  `/workspace/DEBiLGI`, без этого тихо импортируется не тот код.
- Тесты: `PYTHONPATH=$PWD/src .venv/bin/python -m pytest -q -p no:cacheprovider` (~2–2,5 мин).
  Линт: `.venv/bin/ruff check src tests scripts`.
- Бокс иногда приостанавливается: одиночные выбросы на десятки секунд с cpu≈wall — не регрессия кода,
  проверять повтором пары.
- Изменение `language/*.py` меняет ANALYSIS_VERSION → разовая пересборка кэша (~1 мин), это не регрессия.
  Прогрев сида делать после последней правки `language/`.

## Как работать точнее
1. **Сначала воспроизвести, потом чинить.** Прогнать конкретную фразу/сценарий и посмотреть трассу
   (`language_response_trace_steps`, `scores[].rejection_reasons` арбитра), найти причину в механизме.
   Не подгонять поведение под пример: «рад»→«рядом» оказалось ярлыком оценки на наречии, а не созвучием.
2. **Минимальная правка по причине.** Новое поведение — через опциональный флаг/путь, а не через смену
   общих читателей (`parse_proposition`, `reader_goal`), чтобы проба 117 осталась идентичной.
3. **Правки файлов — через Edit с проверкой.** Если правишь скриптом `str.replace`, проверяй, что замена
   реально произошла (число вхождений = 1), иначе правка тихо не пишется.
4. **Каскад контекста:** улучшенный ответ меняет контекст следующего хода; сравнивая с контролем,
   разбирай ход за ходом, прежде чем считать потерю регрессией.
5. **Каждое утверждение в отчёте — с цифрой или ссылкой на файл/тест.** Не писать «работает», если не
   проверено. Неизвестное так и помечать.
6. База сравнения — копия исходников **начала этапа** в `/tmp/debilgi-4NN/before`, не HEAD.
7. Отчёт `LAST_MESSAGE*.md` — по-русски: статус, что сделано и почему (причина), проверки с цифрами,
   что не прошло и почему.
